# 公共站点重构反思

## 任务结论

公共首页不能只是项目 README 的视觉化版本，公开文档也不能用少数概览页同时承担上手、概念、部署和参考。可用的首版需要从读者任务出发：先让用户选路径并完成一次真实调用，再分别解释树、权限、密钥、宿主与 Provider，最后用参考和排障页把事实串回操作旅程。

首页采用一套单一产品母题更有效：路径、节点、scope 与请求流既能形成品牌视觉，也能展示真实模型。交互式身份裁剪、Discover/Inspect/Call 和部署切换比通用终端截图更能证明产品是什么。

## 过程中暴露的问题

- 仅扩写文字仍会复制错误假设。交叉契约审阅发现 capability 真源是 `~describe`，Provider 的节点级与工具级 `~help` 是两阶段流程；把所有动态事实都归给根 `~help` 会直接误导客户端实现。
- “Fetch 风格 API”不等于“可运行在 Workers”。当前公开 SDK 是 Node 22+ 产物，而且没有 SearchIndex 注入面；公共文档必须按实际发布产物而不是内部依赖能力承诺宿主。
- 两种 Cloudflare 路线不能合并成一页。Deploy Button 模板没有 D1 Search，完整源码 gateway 才装配 D1 与完整 gateway 能力；它们的密钥生成和恢复边界也不同。
- 只通过类型检查和构建仍不够。真实浏览器检查发现工具级 `~help` 演示虽然语法正确，却仍展示了节点工具列表；视觉交互也必须接受契约审阅。
- shell 代码块里的 `<placeholder>` 会被 shell 当成输入重定向。号称“可复制”的命令必须使用安全变量或明确字面值；敏感凭证也不能展开进 argv。

## 已吸收的稳定知识

- 任务型公共文档结构、动态事实入口、Cloudflare 两种形态和站点验证闸门已提升到 `overview/project-overview.md`。
- 公共站点用构建产物链接检查保护 24 页导航，旧 URL 通过永久重定向迁移。
- 视觉验收至少覆盖桌面、窄屏、横向溢出、浏览器 console、身份切换、流程 tab、部署 tab 和 Starlight 移动菜单。

## 后续提醒

- 新增或改变 Provider、Search、SDK 宿主能力、CLI 输出或部署绑定时，同轮重新评估公开站点；不要等发布后再补。
- 首页中的示意数据也属于公共契约表达。即使标注为示例，也应遵守节点级/工具级 help、scope 裁剪和出站身份边界。
