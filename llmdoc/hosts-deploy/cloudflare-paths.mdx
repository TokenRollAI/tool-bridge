# Cloudflare 初始化、部署与验收

Cloudflare 是一种宿主,不是业务真源。仓库中的 `packages/gateway/wrangler.jsonc` 必须保持账户中立:不提交 account ID、域名、D1/R2 ID 或环境凭据。真实账户与资源 ID 由 provision 回填,不提交。

Cloudflare 适配器(源码部署与 Deploy Button 模板一致):D1(TB_STATE/TB_SEARCH 双 binding 指向同一个库,见 [state-store-decision](./state-store-decision.mdx))、R2、Durable Objects、Static Assets 与 Cron Trigger。KV 已全面撤出,template 同样包含 D1 search 和 Store cleanup——template 与源码部署是同一个产品,不是缩水形态。

## 推荐入口

从源码 checkout 运行:

```bash
tb init cloudflare --repo .
```

向导负责生成 Admin SK、配置 secrets、创建资源、部署并做基础验证。非交互环境可显式传入 `--account-id`、`--domain` 与 `--yes`;完整选项以 `tb init cloudflare --help` 为准。

手工流程只用于调试:

```bash
pnpm provision
pnpm verify
pnpm turbo run build
pnpm --filter @tool-bridge/dashboard build
pnpm --filter @tool-bridge/gateway run deploy
```

`provision` 从环境读取账户与命名前缀,幂等创建 default Store/Context 共用的 R2 bucket 与一个 D1 库(TB_STATE/TB_SEARCH 两个 binding 指向它),并把本地 checkout 的部署目标写入 wrangler 配置。该写回含环境标识,不应作为通用模板提交。

## Production GitHub Actions 部署

Production 由 `.github/workflows/ci.yml` 管理。GitHub Actions 的 `production` environment 保存一项 secret `CLOUDFLARE_API_TOKEN`,以及 variables `CLOUDFLARE_ACCOUNT_ID`、`TB_CF_BASE_URL`、`TB_CF_DOMAIN`、`TB_CF_NAME_PREFIX`、`TB_CF_D1_DATABASE_ID`;这些账户、域名和资源 ID 不进入仓库。`main` push 只有在 `scripts/deploy-change-filter.mjs` 判定 Cloudflare 运行时相关路径变化,且 verify、全仓 build/打包与部署产物检查全部通过后才执行 production deploy;纯文档或无关客户端变化不部署。

CI 调用 `pnpm provision` 时固定设置 `TB_PROVISION_CONFIG_ONLY=true` 与 `TB_PROVISION_D1_DATABASE_ID`,只把既有账户、路由、R2 名称和同一个 D1 ID 回填进账户中立的 Wrangler 配置,不会创建或查询云资源。R2/D1 resource provisioning 仍是首次部署前的**一次性 bootstrap**(`tb init cloudflare` 或人工 `pnpm provision`),不得塞进每次 deploy。Wrangler 的 `*/15 * * * *` Cron Trigger 属于版本化部署配置，不是 provision 创建的外部资源；源码配置与 Deploy Button template 都必须保留。需要绕过变更过滤手动重部署 Cloudflare 时,从 `workflow_dispatch` 选择 `deploy=cloudflare`;它仍须通过同一组 CI 门禁。

CI token 至少需要目标 Account 的 **Workers Scripts Write** 与目标 Zone 的 **Workers Routes Write**。推荐从 Cloudflare 官方 **Edit Cloudflare Workers** token 模板创建,再把 Account Resources 收紧到生产账户、Zone Resources 收紧到实际域名所在 zone;不要给全账户/全 zone。因为 CI 固定使用 `TB_PROVISION_CONFIG_ONLY=true`,日常 deploy 不调用 D1/R2 resource API,无需为了每次发布给 token 追加 D1 或 R2 资源管理权限;一次性 bootstrap 应使用独立的人工作业或凭据。

Wrangler 打出 worker/assets 已 Uploaded 只代表上传阶段完成,随后仍会更新 `/zones/.../workers/routes`;若 token 缺 Workers Routes 权限,该阶段会以错误码 `10000` 失败。部署成功的唯一判据是 deploy 命令最终成功退出,不能凭中间 Uploaded 日志或公网健康检查判定——健康检查可能命中旧版本或已上传但尚未完成路由更新的版本,不能替代 CI job 结果。

## D1 延迟配置

gateway 已按请求使用 D1 Sessions API，但**代码接入与数据库启用读复制是两步**：

1. 在 Cloudflare Dashboard 打开 `D1 → <数据库> → Settings → Read Replication`。Wrangler 当前没有对应的启用命令，`provision` 会提醒但不会伪装成已经开启。
2. State session 用 `first-primary`：每个 HTTP 请求的首个权威查询必须看到最新 SK/权限/节点状态，保留吊销即时生效；同请求后续查询可由满足 bookmark 的副本服务。
3. Search session 也用 `first-primary`：首次惰性建表后若立即从尚未同步 schema 的副本读取会报错；首查询钉 primary 后，同 session 的后续候选查询仍可由满足 bookmark 的副本服务并保持 read-my-own-writes。
4. DeviceSession DO **不跨 hibernation 复用 D1 session**：每条独立的状态/搜索操作链按同样约束新建 session，hibernate 后复用会带着失效 bookmark。
5. `D1StateStore.getMany` 把分块 statement 放进一次 `batch()` 减少网络往返；schema gate 仍按 isolate/DO 实例复用。

`wrangler.jsonc` 默认启用 Smart Placement。所有鉴权请求至少访问一次 State primary，把 Worker 放近主要后端可减少单请求内连续 D1/上游往返的跨区成本。当前 Dashboard 仍是 `assets.run_worker_first=true`，所以 `/ui` 静态资源也会先到 Smart-Placed Worker；这是核心 API 延迟优先的明确取舍。若要同时追求全球静态资源最低 TTFB，应把 UI 拆到 edge-first Assets/Pages Worker，再用同源或明确 CORS 接 API，不能只改 `run_worker_first` 让 SPA 吞掉 API 路由。

性能诊断不靠体感：

- 响应 `Server-Timing` 含 `tb-worker`，有 D1 查询时另含 `tb-d1`（D1 等待时间总和）。
- 总处理时间达到 500ms 时，Workers Logs 写一条 `event=tool_bridge_slow_request` 的结构化 warning，包含 D1 调用数、wall/SQL 时间、`served_by_region`、primary/replica 次数、入站 colo；不记录 SQL、key、参数、SK 或返回值。
- D1 SQL time 很低但 wall time 很高，优先查 primary/replica 区域和网络往返；两者都低但 `tb-worker` 很高，继续查外部 provider、R2/DO 或应用 CPU。
- 兼容日期必须与仓库锁定的 workerd 可验证上限一致；升级 Wrangler/Miniflare/workerd 后再同步推进，不能把“最新日期”写成测试无法启动的配置。

## gateway 双入口与三条发布路径

`@tool-bridge/gateway` 有两个入口:包根是零插件库入口;`./full` 是全量装配入口(内置插件目录 + D1 search)。到 Cloudflare 的发布路径有三条,必须保持同形态:

1. 源码 wrangler 部署:main 为 `packages/gateway/src/deployEntry.ts`。
2. npm 消费:`@tool-bridge/gateway/full`。
3. Deploy Button template:`template/src/index.ts` 导入 `/full`。

一致性要求:

- 改 gateway 装配(插件目录、search 后端、入口 wiring)时,三处同轮核对,不允许某一条路径掉队。
- template 的依赖版本要与当轮发布的 gateway/dashboard minor 对齐:0.x 下 caret 不跨 minor,template 停在旧 minor 就装不到新装配。
- gateway minor 若改变 search 后端或搜索能力,除同步 template 的 0.x 依赖 pin,还要同轮核对 `template/wrangler.jsonc` 等面向部署者的 search binding 文案;旧实现描述会让模板即使装到新包仍暴露错误运维模型。
- `/full` 不只是 fetch app，还导出 scheduled Store cleanup handler；源码与 template 的 Wrangler 都必须配置同一个每 15 分钟 Cron。只同步代码、不配置 trigger 会让过期 session/share/call capability 与 orphan 永久积累。

会复发的构建坑:给 Workers 目标 bundle 含 `@modelcontextprotocol/sdk` 的入口时,tsup 的 `platform: 'neutral'` 必须设 esbuild `conditions: ['workerd', 'worker', 'browser']`;否则 `pkce-challenge`(exports 只有 browser/node 分支)解析失败。

## 必需安全配置

- 首次引导必须预置 `TB_BOOTSTRAP_ADMIN_SK`,并保存在密码管理器;不得从日志回收最高权限凭据。
- SecretStore 的加密密钥必须通过 Wrangler secret 注入,不进入 `vars` 或仓库文件。
- default Store 缺省复用 `TB_STORE_TOKEN_SECRET ?? TB_SECRET_ENCRYPTION_KEY` 作为根，再做版本化域分离
  SHA-256；派生 HMAC key 不落 D1。通常无需新增 Store secret，显式 `TB_STORE_TOKEN_SECRET` 只用于独立
  轮换域，且同样必须走 Wrangler secret，不能进入 `vars`。
- 上游默认只允许 HTTPS;`TB_ALLOW_INSECURE_HTTP=true` 仅供本地验证。
- 跨实例联邦 search 必须给每个 Worker 部署显式、稳定且全局唯一的 `TB_INSTANCE_ID`；否则仍有 D1
  local search，但不广告 `search:federated`。`TB_SEARCH_FEDERATION_*` vars 可收紧 source/concurrency、
  deadline/return reserve、remote body 和 session TTL，具体默认值与 Node/SDK 共用 core parser。
- 自定义域名、canonical origin 与 OAuth redirect 必须一致;未配置域名时使用 workers.dev/preview 入口。

## Default Store、R2 直传与 CORS

`TB_R2` 是 Cloudflare standard host 的必需 default Store driver；Store 元数据/session 在 D1，字节在 R2 的
`__tool_bridge_internal__/store/v1/...` namespace；旧 `store/v1` 只属于未发布预览，不再保留给 Store，
已有同名 Context prefix 继续可用。R2 binding 自身不提供 presign。要让 Store/Object Context 直传或既有大对象
`$ref` 走 presigned GET，必须同时配置 `TB_R2_S3_ENDPOINT`、`TB_R2_BUCKET`，并把最小权限 R2 API
凭证存入 SecretStore 保留名 `r2-presign`（或 Wrangler secrets `TB_R2_ACCESS_KEY_ID` /
`TB_R2_SECRET_ACCESS_KEY`）。

没有 signer 时 default Store 仍可用，create 会选择 Worker relay，`TB_STORE_RELAY_MAX_BYTES` 缺省为
90 MiB（保守低于 Workers 最低公开 plan 的 100 MB request-body limit）。已知 size 超限在 create 阶段
`rate_limited`；未知/虚报 size 仍可能在 Worker 代码运行前收到平台原生 413。超过有效 relay 上限的对象
必须配置 signer 且在 create 声明精确 size；Store 只有 `presignPutExact` 把 `Content-Length` 纳入签名时
才 direct，否则继续 relay。direct 使用完整 `TB_STORE_MAX_OBJECT_BYTES` 上限，缺省 256 MiB。平台限制以
[Workers limits](https://developers.cloudflare.com/workers/platform/limits/)为准。

Context 写 grant 使用独立的 `TB_UPLOAD_GRANT_TTL_SEC`；Store session/share/read 分别使用
`TB_STORE_UPLOAD_TTL_SEC`、`TB_STORE_SHARE_TTL_SEC`、`TB_STORE_READ_TTL_SEC`，都缺省 900 秒且最大
604800 秒。Dashboard direct upload 要求 R2 bucket CORS 精确允许 Dashboard origin、`PUT`、
Store grant 返回的 `Content-Type` / `Content-Length` / `If-None-Match`（Context grant 无定长要求），需要
读取 etag 时 expose `ETag`；设备与 CLI 不受浏览器 CORS 限制。

Workers 没有常驻进程，也不在普通请求中做全局扫描。`deployEntry.ts` 的 scheduled handler 调
`cleanupDefaultStoreFromEnv`，每 tick 使用短生命周期 D1 session/R2 adapter；清理分页 cursor 持久化在
D1，单次工作有界并可由下一次 Cron 继续。源码与 Deploy Button 的 `triggers.crons` 都是
`*/15 * * * *`，变更发布入口时必须对拍。

## 验收层次

1. 本地:`pnpm verify`,以及发布/打包相关改动的全仓 build。
2. 部署产物:确认 Worker 与 Dashboard 实际加载的是本轮构建,而非旧 `dist`。
3. 基础 smoke:健康检查、Admin SK 鉴权、受限 SK 的 allow/deny/404 语义。
4. Store 离线验收:确认 source/template 都有 Cron、无 signer 的 90 MiB effective limit、capability path 日志脱敏，以及 relay PUT 即 ready。
5. 按需真实验证:MCP、search、device、plugin、R2 direct 等脚本必须显式提供 URL 与 SK。

真实云资源和上游会产生费用或副作用;每轮最多执行一次,需获得用户授权并把证据留在 PR/CI,而不是写进 llmdoc。

共享开发部署可重置,不承担旧预览状态兼容责任。
