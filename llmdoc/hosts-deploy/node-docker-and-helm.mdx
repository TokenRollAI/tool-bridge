# Node 自托管部署

标准交付是单个 Node 应用进程加 PostgreSQL 与通用 S3 兼容对象服务。Redis 可选，仅服务跨副本设备路由；数据库、S3 和 bootstrap 都必须持久保存。默认完整 Compose 不需手填 `.env`，首次通过本机配对完成安装；产品配置边界见 [受管理配置](./managed-configuration.mdx)。

## Compose 与镜像

根 `docker-compose.yml` 用于本地构建，`deploy/compose/docker-compose.yml` 使用已发布镜像。默认栈包含独立 init、PG、SeaweedFS、init-bucket 与 app；镜像版本/摘要以清单为准，不在知识里手抄。init 自动生成应用/管理员数据库凭证和 S3 installer/应用凭证，最小权限文件分别只挂到需要的服务。app 只拿 bootstrap 卷，不挂 Docker socket；对象字节只在对象服务的数据卷。

首次启动检查 init 完成、PG/S3 可用、受保护配对、setup ready 与业务授权调用。`/healthz` 在安装态仍能成功，这是为了让安装面存活；不能把 Docker HEALTHCHECK healthy 当作安装已经完成。首次安装、重新构建应用和重启 PG/S3 是不同验收，必须分别证明身份、配置和对象字节仍可恢复。`down` 与删卷重置不同，清空卷必须是明确的数据丢弃操作。

正式镜像同时携带应用、Dashboard 和官方 PG dump/restore 客户端，运行用户无 root 权限；installer 的初始化容器才执行所需 owner 设置。镜像构建不得依赖宿主已存在 dist，Node 二进制与运行基础镜像也必须匹配。runtime 基于 Node slim，安装官方 PGDG client 工具，不继承数据库 server 镜像及其隐式 VOLUME。

## 探针、反向代理与关停

- `/livez` 证明进程存活，PG 抖动不能触发 liveness 杀进程。
- `/healthz` 返回版本、实例和安装状态，适合进程/安装面检查。
- `/readyz` 在业务未初始化、恢复、维护或 draining 时返回 503；运行态检查 PG、已配置 Redis 与 active S3。需要摘流量的编排器使用 readiness。

平台仅可注入 `PORT` 与受保护 bootstrap 位置；业务设置在 PG。代理须保留 Host、Authorization 与 WebSocket upgrade。TLS 在代理终止时，`canonicalOrigin` 是 Store URL protocol 的信任根，对外 alias host/port 仍取当次请求；不信任客户端 `X-Forwarded-Proto`。

SIGTERM 经 managed shutdown 先标记 draining，让 readiness 立即失败；等待本副本已成功应用的 `shutdownDrainSec` 后关闭 listener 并完成请求、设备与后台工作排空。等待窗口仍可承接编排器尚未摘除的流量；pending 配置不改变该窗口；维护 quiesce 暂时移除 business 时仍用此前已应用的窗口，读取时长不能再依赖 PG 可达。main 必须调用这一实际生命周期入口，不能绕过等待直接 close。

所有实际 HTTP 请求都进入排空计数，响应头返回不代表请求完成。`responseLifecycle.ts` 将释放延至 body 完成、取消清理结束或上游错误；保持背压、不预取，并在消费者暂停时也处理上游错误。只有执行 quiesce 的当前维护调用能通过 AsyncLocalStorage 释放自身一次；不得按原始 URL 前缀猜调用归属，编码、大小写和别名不能改变该规则。

`TbServer.close` 复用同一个 closePromise，但必须先释放当前维护调用，再复用已经开始的关停，避免彼此等待。managed listener 排空后还要关闭维护途中 reload 出的最终 runtime，不能让进程退出遗留其登记。正常请求、响应流与后台工作结束后才释放 runtime 登记和共享锁。慢 cleanup tick 不重入，首轮在监听后异步执行。

## 受限部署执行器

`system/deployment`、`tb deployment` 与 Dashboard 管理 desired revision、observed/effective 配置、agent presence 和 job 状态。保存设置不会直接执行 Docker。管理员在部署主机运行 `tb deployment agent`，明确选定一个 Compose 文件和 `app` 服务，执行器只接受 schema 中的镜像、published 端口/绑定地址和受限目录设置。

agent 比较 Compose 声明与实际容器观察，校验实例身份并领取 job lease，然后执行固定 Docker 子命令。目录必须 realpath 位于选定 Compose 目录内；拒绝 symlink 越界和 Docker socket。bootstrap 目录迁移先停 app，复制持久文件并设安全权限，不搬 PG/S3 数据。省略 `uiDirectory` 表示恢复镜像内 Dashboard，必须删除固定目标 `/app/dashboard` 的旧 mount，而非继续保留旧目录；其它挂载保持原义。

应用后除实例和 UI 健康检查，还要 inspect 真实容器并逐字段比较镜像、端口、绑定地址和可选目录，吻合才能提交成功 receipt。未配置 UI 目录时该 mount target 必须不存在；named volume、tmpfs 或缺 source 的 UI 覆盖不能投影成“未配置”，无法可靠移除的继承挂载必须拒绝并回滚。Docker Desktop 的主机路径只允许与预期路径精确对应的 `/host_mnt` 归一，不得宽松剥前缀掩盖错误挂载。失败恢复旧 Compose 并验证旧实例；健康成功但 receipt 未确认时明确暴露歧义，不直接重试。

该执行器目前是单本机 Compose app 的受限管理器，不是任意 shell/远程部署系统，不自动操纵 Railway 或 Kubernetes 配置。平台变更由平台 CLI/编排器操作，数据库/根轮换由 [专项维护](./maintenance-and-keys.mdx) 处理。

## Railway 与 Helm

Railway 使用 `Dockerfile.railway`；由于平台构建器约束，镜像不声明 VOLUME，由平台把持久卷挂在 `/data`。平台提供的数据库/对象服务连接经受保护 setup/defaults 输入，不引回旧 env-only 产品配置。新实例、已有实例恢复、数据库角色权限和 S3 内网 origin 都必须按实际平台核验，不从“容器部署成功”推导生产闭环成功。

平台挂载的 `/data` 可能由 root 拥有；应用必须同时能写 `/data` 和 `/data/bootstrap`。`proper-lockfile` 会在被锁目录旁创建 `/data/bootstrap.lock`，只修改 bootstrap 子目录 owner 仍会在初始化身份之前失败，并表现为恢复态。受限平台启动阶段先以 root 设置两目录的 owner/mode，再降权运行应用：

```sh
install -d -m 700 -o 1000 -g 1000 /data /data/bootstrap &&
  exec setpriv --reuid=node --regid=node --init-groups node /app/dist/main.js
```

启动阶段需要已获得 root 权限；最终 Node 进程仍以应用用户运行，不以放宽目录权限或长期 root 运行绕过锁文件要求。

私网 S3 的信任锚必须由本机写入权限为 `0600` 的 `install-defaults.json`，以 `storage.endpoint` 固定允许的 exact origin；公开 setup body 无权授予内网例外。独立 `databaseAdminUrl` 也属于该受保护文件，不能塞入公开 setup 请求。经容器 loopback 完成安装时，请求 body 必须显式带 `settings.canonicalOrigin` 的公网 HTTPS origin：只写 `defaults.settings` 会被 setup schema 生成的默认 settings 覆盖。setup 响应的 `baseUrl` 是请求 origin，此时仍为 loopback；交付客户端 profile 时应使用实际公网 origin。

Railway 私网的 SeaweedFS 使用 IPv6 监听 `-ip.bind=::`，`-ip` 与 `-master.peers` 使用稳定私网 DNS 名称。沿用 Compose 已验证的固定镜像和 `volume.max=32`；该值是逻辑卷槽上限，不是托管磁盘的 GB 数。内部 metadata 集合也占卷槽，按物理卷容量随意缩小该值会让业务桶无法写入；创建桶成功不能证明剩余卷槽足以写对象。

Helm chart 部署同一 managed 服务，PG/S3 由外部供应，用户仍先配对初始化。单副本 bootstrap PVC 是默认；多副本须使用同一 initialized bootstrap 的共享卷和共享 PG/S3，并显式配置 Redis。不要把每个 Pod 的独立 setup/root 当成同一实例。

## 多副本设备路由

Node DeviceHub 保有本副本活 socket，DeviceRouter 通过 Redis 路由到持有连接的副本。registry presence 是可见性提示，不是 socket 归属权威；跨副本调用的 `completed|not_dispatched|unknown` 仍遵守单次执行语义。Redis 中断会使路由不可用，不能退成“在线但随便发到本地”。

服务器以 PG replica registry 和共享 session lock 登记 runtime；没有 Redis 时拒绝启动第二个活跃副本，持久数据库 fence 与 key maintenance fence 也阻止不安全登记。多副本运行与停写维护不同：维护要求其它副本正常 drain 并删除登记，过期 heartbeat 或断开的 session 都不能替代该证明；崩溃残留走 [离线恢复边界](./maintenance-and-keys.mdx)。

## 部署验证

`pnpm verify` 与 `pnpm turbo run build` 是工程底线，不能替代生命周期验收：关停设置用真实子进程 SIGTERM 与未结束请求验证；维护从实际编码/别名 HTTP 入口进入，并与阻塞写入、并发 SIGTERM 组合验证写入完成和最终登记清空；真实慢响应验证 body 完成/取消/错误前的计数与背压；可选目录清空核对实际 Compose mount 与镜像内 UI。后端测试使用隔离本地 PG/S3/Redis，先完成 server.close 再删除 schema，不能为错误 teardown 顺序削弱生产租约 guard；缺 env 不静默跳过；部署还需验证持久性和失败回滚。真实平台验证遵守授权与每轮一次资源约束，证据留在验收记录，不把运行 URL、资源 ID 或测试次数写入知识。
