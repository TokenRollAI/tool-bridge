# Node、Docker 与 Compose/Helm

`@tool-bridge/app` 承担宿主中立业务;`@tool-bridge/server` 为 Node 装配状态存储(SQLite 或 PostgreSQL)、文件对象存储、WebSocket 与 HTTP 监听。它不是 Cloudflare gateway 的兼容壳。Cloudflare 专属的 R2/D1、Durable Object 与 Wrangler 配置不得下沉进 server;Node 的 SQLite/PG/文件语义也不得反向泄漏进 app。

## Node 配置边界

- `TB_DATA_DIR` 持有 SQLite(未用 PG 时)和对象数据,应挂载持久卷并限制文件权限。对象存储缺省始终是本地 FS,即使状态在 PG：default Store 最终字节位于 `TB_DATA_DIR/objects/__tool_bridge_internal__/store/v1/...`（容器缺省对象根 `/data/objects/...`），未落位字节集中在 `TB_DATA_DIR/objects/.tb-store-staging-v1`；Context/`$ref` 走同一 driver 的其他 namespace。多实例部署下本地字节不共享(外置见下文 S3 节)。
- default Store 是标准 Node 装配的必备能力。端口监听成功后异步执行首次有界 cleanup，随后每 `TB_STORE_CLEANUP_INTERVAL_SEC` 周期执行（缺省 900 秒）；历史数据再多也不阻塞 readiness，timer 不阻止进程退出，慢 tick 未结束时跳过并发 tick。每个 tick 只扫一次独立 staging 目录。自动清理不扫描未发布预览曾使用的 `objects/store/v1/**`：该路径也可能属于 Context，temp 文件名不能证明 Store 归属；试用过预览的部署须人工确认后再处理残片。清理失败只记录固定事件名，不输出 driver key。
- 首次引导必须设置 `TB_BOOTSTRAP_ADMIN_SK`;缺失时启动默认 fail closed。`TB_ALLOW_INSECURE_BOOTSTRAP=true` 只用于一次性本地开发。
- `TB_ALLOW_INSECURE_HTTP=true` 只放行本地 HTTP 上游,不应进入公网部署。
- 反向代理必须保留 WebSocket upgrade、Authorization 和原始 host/proto 语义。

## 健康探针与优雅关停

三个免认证端点分工明确,k8s 探针按此接线:

- `/livez` → 恒 200(进程存活;liveness)。后端断连**不算死**——liveness 探后端会让编排器在 PG 抖动时错杀健康进程。
- `/readyz` → 就绪探测:Node 宿主逐后端连通性检查(PG `SELECT 1`、Redis `PING`,各限时 1s)+ draining 状态;任一不通或 draining → 503,编排器摘流量。SQLite/FS 无长连接可断,checks 为空恒 200。Workers/嵌入宿主未注入探测器,恒 200。
- `/healthz` → 版本 + catalog digest(三宿主对拍用),容器 HEALTHCHECK 用它。

关停顺序(SIGTERM):置 draining(`/readyz` 立即 503)→ 等 `TB_SHUTDOWN_DRAIN_SEC` 秒(缺省 0;k8s 建议 5–10)→ 停止接受新连接、既有请求跑完 → 终止设备 WS → 关后端。镜像不写死 `ENV TB_PORT`,平台注入的 `PORT` 真实生效,HEALTHCHECK 同步读 `TB_PORT ?? PORT ?? 8787`。

## PostgreSQL 后端

设 `TB_DATABASE_URL` 则 StateStore 与 SearchIndex 都走 PG(共用连接池),缺省回退 `TB_DATA_DIR` 下的 SQLite。两者是独立后端句柄,可分别替换。

- **不需要任何 PG 扩展**,连接角色只要能建表即可(受限托管环境常不给建扩展权限)。
- 全文检索是纯 `ILIKE` 子串匹配,与 SQLite/D1 的 FTS5-trigram 语义对齐;跨后端等价性由共享黑盒契约 `verifySearchIndexContract` 守住。
- 故意不建 trigram GIN 索引:候选查询是三列 `OR` + `LIMIT`,规划器在节点上限满载时一律选 Seq Scan,索引从不被用,却让插入慢数倍、表体积大数倍。放宽节点上限时需连同查询形状重新评估。
- 索引写路径在事务开头取 advisory lock 串行化:容量判定依赖 `COUNT(*)`,无锁时并发 mutation 会各自读到旧计数而突破上限。
- **切换后端不迁移数据。** 给已运行的 SQLite 实例设上 `TB_DATABASE_URL`,得到的是空 PG 状态,首次启动重新走引导;回滚同理,PG 侧写入不回流。跨后端搬迁需自行导出/导入并重建搜索索引。

## Compose 开发栈(根目录 docker-compose.yml)

```bash
pnpm compose:up      # SQLite 后端(默认栈,127.0.0.1:8787)
pnpm compose:smoke
pnpm compose:down
pnpm compose:pg:up   # postgres + gateway-pg(127.0.0.1:8788),pg profile
pnpm compose:pg:smoke
pnpm compose:pg:down
```

两条栈是**两套独立数据**:PG 栈不带 `/data` 卷里的树、SK 与 secret,自己重新引导。`smoke` 全程走 HTTP、与状态后端无关,两边共用同一套断言——这正是后端对等的验收方式。`pnpm compose:reset` 会删除**两条栈**的所有卷,运行前先确认目标只是本地开发状态。Compose 默认值仅用于本机闭环,不是部署模板。

## 生产 Compose(deploy/compose/)

`deploy/compose/docker-compose.yml` 是生产参考栈,与 dev compose 是两回事:无测试装置,secret 全部 `:?required`(缺失时 compose 启动前报错,不会起一个 fail-closed 循环重启的容器),PG 用标准 `postgres:16`。

- `--profile default`:gateway + postgres 单副本。
- `--profile ha`:双 gateway(`TB_REPLICA_ID` 显式 a/b)+ Redis 路由 + Caddy LB。是**单机** HA 参考栈,机器仍是单点;真多副本走 Helm。
- 双副本共享 default Store 与 `$ref` 对象要求配 `TB_OBJECT_STORE_*`;compose 无渲染期校验,只能靠注释提醒(Helm 有硬校验)。
- gateway healthcheck 打 `/readyz`(非 `/healthz`):后端断连时容器转 unhealthy,`restart: unless-stopped` + LB 依赖才有意义。

## Kubernetes(deploy/helm/tool-bridge)

Helm chart 按后端配置自动推断形态,无独立 mode 开关:

- **standalone**(缺省,`postgres.url` 空):StatefulSet + RWO PVC,副本恒 1。用 StatefulSet 而非 Deployment+PVC 是为避免 RWO 卷上滚动更新的"新 Pod 等旧 Pod 释放卷"死锁。
- **HA**(`postgres.url` + `objectStore.*` 配齐):无状态 Deployment,`/data` 用 emptyDir,`maxUnavailable: 0` 滚动;`replicaCount > 1` 还必须配 `redis.url`。
- 危险组合(`replicas>1 + SQLite`、objectStore 半配、standalone 开 HPA、缺信任根)在 `helm template` 渲染期 `fail`,与运行时 fail-closed 语义对齐——坏栈根本部署不出去。
- `TB_REPLICA_ID` 用 `fieldRef: metadata.name`;探针三分工 `/healthz`(startup)、`/livez`(liveness)、`/readyz`(readiness);`terminationGracePeriodSeconds` 要盖过 `shutdownDrainSec` + 排空时间。
- Ingress 接设备 WebSocket 必须放长 proxy 读写超时(示例见 `examples/values-ha.yaml`)。
- chart 不打包 PG/Redis,只留 values 接线点;信任根生产建议走 `secrets.existingSecret`,不写明文 values。

## 容器 PaaS(Railway / Fly / Cloud Run / CF Container)

镜像是单容器 + `EXPOSE 8787`,配 PG 后不需要持久卷存状态。端口取 `TB_PORT ?? PORT ?? 8787`;`TB_CANONICAL_ORIGIN` 把 OAuth `redirect_uri` 钉在规范域名,多域名接入必须设置。三个限制:

Railway Metal 不接受 Dockerfile 的 `VOLUME` 指令,因此 Railway service variables 必须设置 `RAILWAY_DOCKERFILE_PATH=Dockerfile.railway`。根 `Dockerfile` 仍是 Fly/Cloud Run/CF Container 等平台的通用入口并保留 `VOLUME /data`;`Dockerfile.railway` 只省略这一条指令,其余镜像行为由 `pnpm test:dockerfile` 保证严格同形。使用本地 SQLite 或 FS 对象存储时,还必须在 Railway 把 Volume **运行时**挂载到 `/data`(平台不会因 Dockerfile 注释自动创建卷);PG + S3/R2 的无状态形态可以不挂卷。不要为选择 Dockerfile 新增已废弃的 `railway.json`/`railway.toml`;若未来要把完整 Railway 项目纳入声明式管理,另行评估新 IaC。

Railway production 使用平台原生 GitHub source 监听 `main`,并开启 **Wait for CI/check suites**:只有对应 main commit 的检查全绿后才开始部署。Watch Paths 只覆盖共享/Server/Dashboard/插件运行时代码、构建清单与 `Dockerfile.railway` 等真实运行时依赖,文档或 CLI/SDK-only 变化不应触发生产重建;路径边界与 `.github/workflows/ci.yml`、`scripts/deploy-change-filter.mjs` 同步维护。首次接线必须等交付这套闸门的 PR 合入 `main` 后再连接 production service,不得在 PR 合入前提前监听 `main`;构建入口仍由 `RAILWAY_DOCKERFILE_PATH=Dockerfile.railway` 指定。原生链路不可用时用 Railway CLI 手动部署作为 fallback,不要回补一套旧 Config-as-Code。

- **ObjectStore 缺省是容器本地 FS**,default Store/`$ref` 大对象在没有持久卷时随容器重建丢失、多副本互不可见;配 `TB_OBJECT_STORE_*` 外置。
- **设备 WebSocket 多副本需配 `TB_REDIS_URL`**;不配时设备只连在一个副本上,调用打到别的副本会误判离线。
- **首次引导需要 `TB_BOOTSTRAP_ADMIN_SK`**,缺失 fail closed,平台上表现为容器反复重启。

结论:**PG + S3 + Redis 三者配齐即可多副本横向扩容**;只配 PG + S3 是单副本无状态形态。

## 多副本设备通道(Redis)

设备的 WebSocket 是**活 socket**,只存在于接受它的那个进程里。副本 B 收到打给"连在 A 上的设备"的调用时,必须把调用**转发**给 A 再收回结果。`TB_REDIS_URL` 启用路由表 + pub/sub 转发;`TB_REPLICA_ID` 缺省用 hostname,同机多进程必须显式给。

- **路由表**(Redis string + 30s TTL,周期续期):`deviceId → 持有者副本 ID`,副本崩溃后条目自动过期。
- **转发**(pub/sub):call 发往持有者频道,result 回发起方回执频道,`correlationId` 关联;有独立超时兜底。
- **本副本持有连接时完全不经这条路**,单副本部署零额外开销、不用配 Redis。
- **回收保护**:`reclaim` 会 `deleteSubtree`(删数据)。多副本下"本副本没有该连接"不等于"设备离线",回收前必须查全局路由;`sweepOrphans` 同理。路由查不通时保守跳过——宁可晚删,不可错删。

对照 Cloudflare 宿主:那边用 Durable Object,天然"每设备一个单点"(见 [do-websocket-sessions](../device/do-websocket-sessions.mdx));本机制是 Node 多副本的等价物。

## 平台对象存储(S3 / R2)

配齐 `TB_OBJECT_STORE_ENDPOINT/BUCKET/ACCESS_KEY_ID/SECRET_ACCESS_KEY` 四项即用 S3 兼容端点(`TB_OBJECT_STORE_REGION` 可选,缺省 auto),缺省回退本地 FS。该 driver 同时承载 deployment-level default Store 与对象型 Context，但 Store 固定使用 `__tool_bridge_internal__/store/v1/...` 保留 namespace；重叠 Context prefix 拒绝挂载，空 prefix 的所有 provider 路径仍会过滤/拒绝 Store key。旧 `store/v1` 只属于未发布预览，不再保留给 Store，已有同名 Context prefix 可继续使用。

- **四项必须齐全,缺一即拒绝启动。** 半套凭证静默回退本地 FS 的错误只在故障时暴露,代价远高于启动即拒。
- 配上后既有 Context `$ref` 可走 S3 presign。default Store 只有在 create 声明精确 size 时才用
  `presignPutExact` 返回 create-only presigned PUT，签名 headers 必含 `Content-Length`；未知 size 一律
  relay。direct PUT 后必须 capability-only complete/HEAD 才 ready。Store owner/share read 当前仍使用独立
  `~store/refs|shares` relay route，不因 driver 有 presign 就改变公开 wire。本地 FS 的 Store 上传走流式
  relay，PUT 成功当次即 ready；Context 本地 FS 仍不声明 `create_upload`。
- `TB_REF_TTL_SEC` 控制下载 `$ref`/presigned GET；`TB_UPLOAD_GRANT_TTL_SEC` 独立控制写 grant，缺省 `min(TB_REF_TTL_SEC, 900)`。两者均钳制在 SigV4 的 `1..604800` 秒范围，放宽慢下载窗口不会把写入窗口一并拉长。
- Store 配置独立：`TB_STORE_MAX_OBJECT_BYTES`（缺省 256 MiB）、`TB_STORE_RELAY_MAX_BYTES`（Node 缺省跟随前者）、`TB_STORE_UPLOAD_TTL_SEC`、`TB_STORE_SHARE_TTL_SEC`、`TB_STORE_READ_TTL_SEC`，以及 `TB_STORE_CALL_MAX_BYTES/MAX_OBJECT_BYTES/MAX_OBJECTS/ALLOWED_CONTENT_TYPES`。显式 `TB_STORE_TOKEN_SECRET` 至少 16 字符；否则复用 `TB_SECRET_ENCRYPTION_KEY` 作根，经版本化域分离派生且不落 StateStore。两者都缺时才 CAS 生成持久 fallback，正式部署不应依赖该逃生路径。
- Dashboard 是浏览器客户端，bucket CORS 必须精确允许 Dashboard origin、`PUT` 与签名 headers（Store
  direct 为 `Content-Type`、`Content-Length`、`If-None-Match`；Context grant 不含定长要求）；需要读取
  etag 时 expose `ETag`。原生设备与 CLI 不受浏览器 CORS 限制。
- 这是**启动期基础设施配置**,不在 Dashboard 里改:运行时换端点会让已写入的 `$ref` 与 `store://default/...` 字节落点失效。按节点用不同存储走 `kind: 'context'` 节点自己的 S3 配置；Store 当前不开放 named driver 热切换。
- Store cleanup 只遍历 StateStore 的权威记录；driver 中没有对应 metadata 的 key 可能属于 Context，绝不
  当 orphan 删除。终态字节删除成功后记录 `bytesDeletedAt`，保留窗口后 CAS 删除 metadata，重复 tick
  不会重复调用外部 DELETE。
- 与 `TB_DATABASE_URL` 组合即完整无状态形态:换全新容器仍能读回一切,有集成测试覆盖。
