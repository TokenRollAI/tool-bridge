# 部署级 Default Store

> **状态：已实现。** `default` Store 是部署级私有对象能力；新设备不需要先挂载 Context，就能把拍照、
> 视频或附件上传为 `store://default/<objectId>`。本文记录当前契约，精确 schema 仍以 core 类型、builtin
> Help 与测试为准。

## 为什么不是 Context

Context 是有业务语义的命名数据源，负责 `list/get/search/write/...` 等 provider 动词；部署者可能只希望
它可读或用于检索，并不希望它成为设备的外挂文件系统。设备产物只需要一个私有、可分享的字节落点，
不应该知道 context path、entry path、bucket key、磁盘路径或 provider 配置。

当前分工如下：

| 层 | 职责 |
|---|---|
| `StoreService` | 对象身份、owner/producer、upload session、幂等、授权、分享、生命周期与清理 |
| `StateStore` | 保存对象/session/capability/share 的权威元数据；并发状态转换必须使用 `compareAndSwap` |
| `ObjectStore` | 保存字节并提供 `put/head/get/delete/list`，可选 `presignPut/presignGet` |
| Context | 语义数据源与命名 entry；可以显式保存 `store://` URI，但不是 default Store |

Store 字节使用独立的 `store/v1/...` driver namespace，不重解释既有 Context 对象。`filename` 只是展示
元数据，不参与 key；object id、upload id 与 driver key 都由服务端生成。

## 对象身份与状态

当前只开放名为 `default` 的 Store，稳定 URI 严格为：

```text
store://default/<22..64 位 base64url objectId>
```

URI 只表示身份，不是 bearer capability；知道 URI 不授予读取权。对象权威状态为 `pending`、`ready`、
`failed`、`abandoned`、`deleted`，只有 `ready` 可读、可分享和进入 owner 的列表。

- `owner` 是稳定 `OwnerRef`，决定普通管理面的对象级授权，不等同于某次调用使用的 SK `keyId`；SK
  轮换不会自动改变对象 owner。
- `producer` 单独记录实际产出者。普通管理面上传时 owner/producer 都是当前 owner；远程设备调用时
  `owner = caller.owner`，`producer = device:<deviceId>`，并记录 `originCallId`。
- ready descriptor 返回稳定 URI、MIME、实测 size、owner/producer 与时间等公开元数据，不返回 driver
  key、upload/share token 或签名 URL。
- 创建请求可声明 size、sha256 checksum、filename 与 owner-scoped `idempotencyKey`。同一 owner、同一
  key、同一声明会恢复原 session/descriptor；声明矛盾返回 `conflict`。

StoreService 构造时强制要求 `StateStore.compareAndSwap`；缺 CAS 的自定义状态后端对 Store fail closed，
不能用进程内锁或 `get→put` 模拟跨副本状态机。capability HMAC key 优先从显式
`storeTokenSecret`，否则从宿主 `encryptionKey`，经 `tb-store-capability-root:v1` 域分离 SHA-256 派生且
不持久化；只有没有任何信任根的自定义/开发宿主才在 StateStore 用 CAS 生成持久 fallback。明文
upload/call/share token 从不写入权威记录，只保存 hash。

## 上传协议

普通 SK 控制面使用 builtin：

```text
POST /system/store/create_upload
POST /system/store/complete_upload
POST /system/store/abort_upload
```

`create_upload` 只接收对象声明，不接收 context/path/overwrite。响应统一包含 `uploadId`、`objectUri`、
`transport`、`method:'PUT'`、`url`、`headers`、`expiresAt`、`maxBytes` 与短期 `uploadToken`。调用方必须把
grant 视为 secret，不记录 URL、headers 或 token。

两种 transport 共用同一状态机：

1. **relay**：客户端向 `PUT /~store/uploads/<uploadId>` 流式发送 body，并用
   `x-tb-store-upload` header 携带 upload token。服务端在流中计数、driver 原子落位后，以 CAS 把对象
   推进 `ready`，该 PUT 直接返回 descriptor；正常路径不再额外 complete。
2. **presigned-put**：driver 能安全签发 PUT 时，字节直接进入 R2/S3。随后客户端以 SK owner 身份，或用
   `x-tb-store-upload` header，调用 `complete_upload`；服务端 HEAD 校验存在性、实测大小与可用元数据后
   才推进 `ready`。

`complete_upload` 幂等；对已经完成的 session 返回同一 descriptor。relay 也可调用 complete 作崩溃恢复
确认，但未成功提交字节时会 `conflict`。`abort_upload` 对未完成对象幂等，ready 对象不可 abort。

每次 grant 的 `maxBytes` 是部署上限、transport 上限与 call 配额的有效交集。已知 size 超限在 create
阶段以 `rate_limited` 拒绝；relay 对未知流逐 chunk 计数，越界即取消并由 driver 清理临时字节。首期只
支持整对象 single PUT，失败重试会从头发送整个对象。

## 远程设备调用

设备帧仍是 JSON，不新增二进制 WebSocket 帧。网关在转发每次 device call 前签发窄能力并写入
`call.context.upload`：

```ts
{
  token: string
  expiresAt: string
  maxBytes: number
  maxObjects: number
}
```

Device SDK 将它封装为 handler 的 `call.uploadObject(...)`。create 请求用
`x-tb-store-capability` header；后续 relay/complete 用本次 upload token。call capability 绑定 caller
owner、device producer、call id、期限、对象数、总字节、单对象大小与 MIME allowlist，只能新建本次
调用的对象，不能 list/read/share/delete 其他对象。call 返回、取消或失败后网关 best-effort revoke，
到期与后台清理是硬兜底。

默认策略是每个 call 最多 4 个对象、单对象 256 MiB、合计 512 MiB、MIME `*/*`；宿主可用
`TB_STORE_CALL_*` 覆盖。设备侧 `maxBytes/maxObjects` 只用于早拒，服务端 reservation/CAS 才是权威。
老网关不下发 capability 时，`call.uploadObject` 明确返回 `unavailable`。

设备也可用普通 HTTP 身份调用顶层 `uploadObject` 做自主上传，此时 owner/producer 都是设备身份。两条
路径最终只把 descriptor/`store://` URI 放进 result，绝不返回上传 capability。

## 读取、分享与管理

`system/store` 的其余命令是 `stat`、`read`、`share`、`revoke_share`、`delete`、`list`：

- `stat/read/list` 的 builtin scope 是 `read`；create/complete/abort/share/revoke/delete 是 `write`。
  scope 通过后仍执行对象级 owner 检查；跨 owner 以 `not_found` 隐藏对象存在性。
- `read(uri)` 返回短期 owner `$ref`，数据面为 `GET /~store/refs/<token>`；获取对象时仍检查对象保持
  ready，因此 delete 会立即使旧 ref 失效。
- `share(uri, ttlSec?)` 只支持有期限、匿名 bearer 下载，返回 share id 与
  `GET /~store/shares/<token>`；share 在 StateStore 中有状态，`revoke_share` 与到期即时生效。
- `list` 只列当前 owner 的 ready 对象并 cursor 分页。`delete` 先 CAS 标记不可读，再幂等删除字节。

capability-only create/complete/abort 路由在普通 SK 认证之前匹配；只有对应 header 存在时才走窄能力，
否则继续进入普通 HTBP 鉴权。`callCapability`、`capability`、`uploadToken`、`shareToken` 等 secret 字段
明确拒绝出现在请求 body。`/~store/refs` 与 `/~store/shares` 的 capability path 在结构化慢请求日志中
必须脱敏；无效、过期或对象缺失统一折叠为 404。

## 宿主装配与清理

| 宿主 | default Store 字节落点 | 上传路径与清理 |
|---|---|---|
| Node 单进程 / 单副本容器 | 缺省 `TB_DATA_DIR/objects/store/v1/...`；Docker 常见为 `/data/objects/...` | 本地 FS 流式 relay；启动前清理一次，之后每 `TB_STORE_CLEANUP_INTERVAL_SEC`（缺省 900 秒）清理 |
| Node HA / 易失容器 | 四项 `TB_OBJECT_STORE_*` 配齐后的共享 S3/R2-compatible driver | 有 signer 时 presigned PUT；半配拒绝启动，多副本不得依赖副本本地盘 |
| Cloudflare Workers | 必需 `TB_R2` binding | 有 S3 API signer 时 direct；否则 Worker relay 缺省收紧为 90 MiB。源码与 Deploy Button 均用每 15 分钟 Cron Trigger 调 scheduled cleanup |
| SDK 嵌入宿主 | `ToolBridgeConfig.objects` 必填，可显式使用 `MemoryObjectStore` 做测试/易失开发 | driver 有 presign 则 direct，否则 relay；StateStore 同样必须提供 CAS；无 encryption/store 信任根时才生成持久 fallback |
| 旧自定义 `TbAppDeps` 宿主 | `objects` 类型仍可缺省以保持装配兼容 | Help 可发现 `system/store`，实际 Store 调用以 `unavailable` fail closed；应迁移为显式 driver |

Node 的本地 driver 逐块写入同目录随机临时文件，fsync 后以 no-replace 原子落位，并流式读取；filename
无法影响路径。R2/S3 signer 不可用时 Store 不消失，而是退到 relay 的有效上限。Cloudflare 超过 90 MiB
的当前路径必须配置 signer/direct；平台仍可能在 Worker 代码运行前返回 request-body 413。

清理是有界、cursor 分页且进度持久化的宿主任务，不由普通请求顺带触发。它收敛过期 upload/share/call
capability/idempotency binding、pending/failed/abandoned/deleted 对象、无元数据 driver orphan 与本地
staging 文件；清理与并发 complete 竞争时必须重新读取状态，不能删除已经 ready 的字节。

## SDK、CLI 与 Dashboard

- 通用 SDK 的 `createStoreClient` 提供 upload/stat/list/read/download/share/revokeShare/delete；上传、下载
  都保持流式，控制面错误会裁剪可疑 URL。
- `@tool-bridge/sdk/device` 提供顶层 `uploadObject` 与 handler 内的 `call.uploadObject`，返回稳定
  descriptor。旧 `uploadContextObject` 已从设备 SDK 删除。
- CLI 提供 `tb store upload|stat|get|share|revoke-share|rm|list`（`list` alias 为 `ls`）。二进制 get
  缺省流向 stdout，`--out` 以 create-only 方式写新文件。只有用户明确执行 `share` 时，成功 stdout/
  JSON 才交付所请求的短期 `$ref`；其他输出与全部错误均裁剪 `$ref`、签名 URL、headers 和 token。
- Dashboard 的 `/manage/store` 是独立 Store 页面，支持上传、分页列表、stat、下载、短期分享/撤销和
  删除；它不复用 ContextBrowser，也不把 capability 写进 toast、调用历史或浏览器 URL。

Context 管理上传仍保留：`ctx put`/Context `write` 用于内联语义内容，Context `create_upload`、
`tb ctx upload` 与 Dashboard Context upload 用于把二进制 author 到指定命名 entry，继续返回
`node://`。它们与匿名产物 Store 正交；不要把 Context upload 悄悄改写成 `store://`。

## 当前限制与后续演进

- 当前只支持 `default`，没有公开 named-store 选择面。
- 当前只有 single PUT，没有 multipart/resumable、分片恢复或弱网逐 part 重试；大视频失败会整对象重传。
- share 当前只有短期匿名下载，没有指定 principal、永久公开 URL 或 CDN 发布。
- 没有主体总占用量/自动淘汰策略；现有硬边界是部署单对象限制与 call 数量/字节/MIME 配额。
- checksum 只在后端返回对应 metadata 时确认并进入 descriptor；客户端声明不能替代实测 size。
- `store://` 尚不自动投影为 MCP image/resource 或 Context `$ref`；消费者须按当次 owner/share 权限显式
  调用 `read`。

multipart/resumable 是明确的未来项，扩展时应新增 part 状态与恢复协议，不得把现有 `attempts` 或
single-PUT session 破坏性重解释。
