# 插件运行时

## 三种来源

内置 plugin 与外部 plugin 共用 `plugin/v2` descriptor 和 envelope，但控制面不同：

| 来源 | descriptor 真源 | 发现/挂载 | 状态 |
|---|---|---|---|
| 内置 | 构建期生成的 `BUILTIN_CATALOG` | `system/catalog`，直接挂载 | 不写 StateStore 注册记录 |
| 外部 HTTP(S) | 注册时抓取并校验 `/~describe` | `system/plugin` 注册后挂载 | manifest/meta/health 落 StateStore |
| 自定义进程内 binding | 宿主显式装配 handler；可按外部注册流程接入 | `binding:<name>` | 只用于宿主自定义，不替代内置 catalog |

`pluginBindings` 说明代码在哪里，`pluginCatalog` 说明它导出什么；标准宿主从 `@tool-bridge/plugins` 同源装配两者。只给一半会得到"能解析不能调用"或"有代码但无法选择 export"。

## catalog 契约

`system/catalog list/search` 每项保留：

- `id`、`digest`、`description?`
- 有序 `exports`
- 展示用的 `nodeKinds`
- 必有的 `exportDetails[exportId]`

`exportDetails` 是 kind、auth、mountConfig 的唯一真源。CLI 和 Dashboard 不再从 provider 级 `needsOAuth`、`credentialFields`、`mountConfigFields` 或 `exportKinds` 猜测选中 export 的行为。

内置 export 必须显式声明凭证形态：`auth:none`、`auth:single`、`credentialFields` 或 `oauth`。`~describe` 必须纯内存、零凭证、零网络，否则无法安全 codegen。

## 调用与密钥

- 节点只保存 `authRef`；SecretStore 保存明文。
- 单值、多字段与 OAuth client 凭证是互斥形态。
- 非敏感挂载配置进入 `providerConfig`，会被 registry get 回显；密钥不得混入。
- plugin 与网关同进程同权，内置 handler 的 env 必须经 `narrowPluginEnv` 白名单收窄。
- plugin 出站必须用 `guardedFetch`；自定义敏感头或 secret body 遇跨源 redirect 应拒绝。
- 未配置 `PLUGIN_TOKEN` 的外部托管 plugin 必须 fail closed；进程内模式由宿主明确标记。

## 注册与解析优先级

同名显式注册记录优先于内置 catalog，允许部署者用自己的实现覆盖内置项。内置项的普通流程不注册、不探活、不写 meta；删除内置节点后，读 `~help` 也不得偷偷把注册状态写回来。

删除/更新 catalog 或 wire 字段时，core、CLI、Dashboard 与 app 集成测试必须同轮改；旧预览客户端不在兼容范围。

## 普通 provider HTTP

内置 provider 的普通 JSON REST 请求只能经 `createProviderHttpClient` 进入 `guardedFetch`。这个零运行时依赖的薄层统一 query/body、响应解码、上游错误映射和 secret 脱敏，但不提供隐式重试：每次请求只执行一次(`retry=0`)。deadline 覆盖 fetch 和异步 response body 消费，不能在收到 headers 后就停止计时；同步 `JSON.parse` 仍在请求操作解决前执行，但 JavaScript timer 无法抢占它，不把这描述成可中断的 CPU wall-clock 上限。

`guardedFetch` 仍是 provider 唯一出站安全边界：初始 URL 和每一跳 redirect 都重做协议/IP 字面量策略，跨源剥离凭证、默认 fail closed。redirect method/body 必须遵循 Fetch 语义：301/302 只把 POST 改为 GET，303 把 GET/HEAD 以外的方法改为 GET 并删除 body headers，307/308 保留 method/body。IP 库只替换地址 grammar，不替换仓库的禁止网段政策。Node/Workers 不共享一致的 DNS 解析门禁，本层故意不检查域名解析结果；DNS rebinding 由部署侧出网策略阻断，不得把 IP 字面量校验误表述为完整 DNS SSRF 防线。

只有流式、协议升级或其他薄层确实无法表达的边界才能保留直接 `guardedFetch`；每个例外都必须在 `provider-http-exceptions.json` 按文件/原因登记，并由策略测试同时拒绝未登记调用和已失效 allowlist。普通 provider 不得自行恢复裸 `fetch`、retry 或另一套错误映射。

### 有界缓冲响应

provider 需要把不可信二进制/文本响应完整缓冲到内存时，使用共享 `readBoundedResponseBytes`，由调用方声明
`maxBytes` 与领域错误。默认可用合法 `Content-Length` 做早拒，但读取过程中仍按实际字节计数，后者才是
最终硬边界；不能先无界 `arrayBuffer()` 再检查大小。超限必须 cancel stream，并在所有路径释放 reader lock。

少数上游若历史契约只信实际流量，可显式关闭声明长度预检，但不得关闭实际字节上限。大字节 Base64 使用
Web-runtime-neutral 的分块 helper，不能重新引入整数组 spread 或 Node-only `Buffer`。这些 helper 只统一
“完整缓冲”原语：它们不是零拷贝/常量内存流式传输，也不替代 `guardedFetch`、deadline、redirect、SSE、
multipart 或 provider 专属 status/error 语义。
